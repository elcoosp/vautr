# ADR 0008: Patch astro-expressive-code code-block language detection

**Status:** Accepted
**Date:** 2026-11-07

## Context

With Astro 7.4 / Starlight 0.42 (Sätteri markdown processor) + Expressive Code
0.44.3, every hand-written fenced code block in the docs content rendered as
`data-language="plaintext"` — monochrome, untokenized — even though the fence
declared a language (`bash`, `ts`, `caddyfile`, …). Code blocks generated by
starlight-openapi on its own pages were unaffected.

Diagnosis (verified by instrumenting `getCodeBlockInfo` in a real build):

- In the content-layer render path, the `code` hast element reaches Expressive
  Code with `properties.className: ["language-bash"]` intact but
  `data: undefined` — the content-layer store round-trip drops hast `data`.
- Expressive Code's Sätteri plugin (`astro-expressive-code` `satteri.ts`,
  `getCodeBlockInfo`) reads **only** `code.data?.lang` and falls back to `""`
  (→ plaintext), while Sätteri's own highlight plugin reads
  `data?.lang ?? className?.slice("language-".length) ?? "plaintext"`.

This is an upstream incompatibility; no configuration option avoids it.

## Decision

Patch `astro-expressive-code@0.44.3` with pnpm's supported patch mechanism
(`pnpm patch` → `patches/astro-expressive-code@0.44.3.patch`, recorded in
`package.json` `patchedDependencies`): `getCodeBlockInfo` now falls back to the
`language-*` class for both `lang` and `meta`, mirroring Sätteri's own
highlight plugin. The patch is three lines of fallback logic; behavior is
unchanged whenever `data.lang` is present.

## Consequences

- All authored fenced code blocks tokenize again (verified: `bash` blocks
  carry colored Shiki token spans; `data-language` reflects the fence tag).
- When upgrading `astro-expressive-code`, remove the patch
  (`pnpm patch-remove`) once the upstream fix lands; re-check highlighting as
  part of the visual QA pass.
