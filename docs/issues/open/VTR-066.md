## What was built (verified scaffolding only)

The server-backed sharing path was missing two pieces that the desktop's local
orchestrator already had. VTR-066 adds them as correct, verified building blocks:

1. **Server: `PUT /users/{user_id}/public-key`** (`core/vautr-server/src/handlers/sharing.rs`).
   Publishes/replaces the caller's own X25519 sharing public key. Enforces
   `caller == user_id` (you may only write your own key). Backs onto the existing
   `Repository::upsert_sharing_public_key` (the `GET` directory endpoint already
   existed). `cargo check -p vautr-server` green.

2. **wasm FFI: `vautr-crypto-wasm` sharing module** (`core/vautr-wasm/src/sharing.rs`,
   registered in `lib.rs`; `vautr-crypto` `sharing` feature enabled in the crate's
   `Cargo.toml`). Exposes:
   - `generate_sharing_keypair() -> Vec<u8>` (`public(32) ‖ secret(32)`)
   - `restore_sharing_keypair(secret: &[u8]) -> Vec<u8>`
   - `share_item(sik, recipient_public, item_uuid) -> Vec<u8>` (`wrapped_sik ‖ ephemeral_pk`)
   - `unwrap_shared_item(wrapped_sik, ephemeral_pk, recipient_secret, item_uuid) -> Vec<u8>` (sik)
   Also added `SharingKeyPair::secret_bytes()` accessor in `core/vautr-crypto/src/sharing.rs`
   so the client can persist/restore the sharing secret.
   Verified: `cargo test -p vautr-wasm sharing` (2 tests, roundtrip) + `cargo build
   -p vautr-wasm --target wasm32-unknown-unknown` both green.

## What is NOT done (the actual feature)

The end-to-end sharing feature (share an item from the extension/web/mobile,
receive in an inbox, decrypt) is **blocked** and intentionally NOT shipped:

- **Blocker — per-item SIK data model.** ADR-007 sharing wraps a *per-item* Secure
  Item Key (SIK); the recipient unwraps `wrapped_sik` → SIK → `deriveDek(sik)` →
  decrypt payload. The server-backed clients (`VautrWebClient` / `@vautr/client-sdk`)
  encrypt **every** item under a single `deriveDek(svk)` vault DEK and do **not**
  track per-item SIKs. To build `wrapped_sik` correctly, the owner needs the
  item's actual SIK, which the client does not have.
  - Sharing `svk` (the vault DEK) as the "SIK" would let a recipient derive the
    whole vault DEK and decrypt **all** items — a critical security violation.
    This is explicitly rejected; no such shortcut is implemented.
  - Fixing it requires migrating the server-backed item-encryption model to
    per-item SIKs (client data model + sync payload + migration) — a real
    backend/client-crypto epic, not a UI port.

- **Not built (deliberately, to avoid stubs):** `VautrMlpClient` sharing surface
  (`getUserPublicKey`/`publishPublicKey`/`createShare`/`uploadSharePayload`/
  `listSharesInbox`/`revokeShare`), the `SharingManager`, and any extension/web/
  mobile sharing UI.
