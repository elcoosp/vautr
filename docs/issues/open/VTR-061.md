## What to build

The secure reveal path for mobile (`MobileVautrClient` + `SecretOverlay` +
native Kotlin/Swift `NativeSecretView`) is fully written (VTR-048) and the
shipping secrets screen now prefers it when the FFI client is present
(`apps/mobile/src/routes/_app.projects.$projectId.tsx`, `lib/client.ts`
`bootVautrCore`). But `getMobileClient()` returns `null` because no compiled
uniffi/TurboModule is linked into the RN app, so the code path is inert and the
screen falls back to `services.api.revealSecret` (plaintext into JS).

Close the gap:
- Compile + link the `modules/vautr-native` Kotlin/Swift uniffi bindings as a
  TurboModule / JSI module (`NativeVautr`) so `initializeVautrCore({ native, ... })`
  succeeds in release builds.
- Wire `globalThis.__NATIVE_VAUTR__` (or the expo/React-Native native module
  registration) so `bootVautrCore` finds it on app mount.
- Add a Maestro/Detox e2e asserting a secret reveal surfaces in the native
  overlay and never appears as plaintext in the JS heap / React state.
- Remove the HTTP plaintext fallback once the native module is the default path
  (keep it only behind an explicit `VAUTR_INSECURE_HTTP_REVEAL` dev flag).

## Acceptance criteria

- [ ] `getMobileClient()` returns a live `MobileVautrClient` in release build.
- [ ] Reveal goes through `SecretOverlay` (`CoreAction::RenderInOverlay`), not
      `services.api.revealSecret`.
- [ ] e2e proves no plaintext secret in JS state during reveal.
- [ ] Mobile reaches the same ZK reveal guarantee as desktop.
