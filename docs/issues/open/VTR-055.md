## What to build

Performance enhancements for FTS5 search:
- Ensure FTS5 tokenizer uses `unicode61` with case‑insensitive matching.
- Add benchmark that inserts 10,000 items and measures search latency for prefix, substring, and exact match queries.
- Implement query rewriting: strip common words (stopwords), handle wildcards.
- Use `LIMIT 100` to bound result sets.

## TDD Instructions

1. **Write a benchmark** (using `criterion`) that searches for a common word (e.g., “bank”) and measures p95 latency – must be < 100 ms.
2. **Write a test** that searches for a prefix like “ban” and returns all items starting with “ban” (using `MATCH 'ban*'`).
3. **Write a test** that searches for a substring like “ank” – FTS5 does not support leading wildcards efficiently; ensure the UI warns about performance.
4. **Write a test** that the search result is ordered by relevance (BM25) – not by date (unless the query is empty).
5. **Write a test** that after rebuilding the FTS5 index (drop and recreate), the search results are identical to before.

Implementation: use SQLite’s FTS5 extension with the `BM25` ranking function. Create a benchmark suite in `benches/search.rs`.

## Acceptance criteria

- [ ] Search for 10k items meets the 100ms p95 target.
- [ ] The index rebuild takes < 2 seconds for 10k items.
- [ ] Empty query returns the top 50 recent items (no FTS).
