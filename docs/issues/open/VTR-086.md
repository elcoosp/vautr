# VTR-086 — Web register fails: "expected 32 bytes, got 154" (mnemonic sealed with SVK wrap)

**Status:** fixed (pending commit)
**Date:** 2026-08-15
**Client:** web (`packages/vautr-client-sdk` + `core/vautr-wasm` wasm)

## Symptom
User: "registration failed on desktop register/finish parse: error decoding
response body" and web "Registration failed." with no request sent. Browser
repro: calling the app `register()` threw `expected 32 bytes, got 154`.

## Root cause
`realClient.register` (packages/vautr-client-sdk/src/realClient.ts:274) sealed the
recovery mnemonic under the KEK with:

    this.crypto.wrapSvk(new TextEncoder().encode(mnemonic), kek)

`wrapSvk(svk, kek)` requires a **32-byte SVK** (wasm `to_arr32`), but the mnemonic
is ~154 bytes → `expected 32 bytes, got 154`. The inverse at line 350 also used
`unwrapSvk`, so the Emergency Kit mnemonic could never be opened either. The
`wasm-pkg` was also stale (Aug 11) vs the current `vautr-crypto` crate.

## Fix
- `core/vautr-wasm/src/auth.rs`: added `seal_mnemonic(kek, plaintext)` /
  `open_mnemonic(kek, ciphertext)` using the same AEAD (`aead::encrypt`/`decrypt`,
  keyed by the KEK, SVK AD) but accepting arbitrary-length plaintext. Added
  `seal_mnemonic_js` / `open_mnemonic_js` wasm-bindgen wrappers.
- `apps/web/src/lib/wasm.ts`: export the two new wrappers.
- `packages/vautr-client-sdk/src/crypto.ts`: `sealMnemonic` / `openMnemonic`
  adapter methods.
- `packages/vautr-client-sdk/src/realClient.ts`: line 274 uses `sealMnemonic`,
  line 350 uses `openMnemonic`.
- Rebuilt `apps/web/wasm-pkg` (wasm-pack build --target web) so the glue + .d.ts
  match the current crate.

Desktop/native paths were unaffected (they use `vautr-crypto`/`vautr-keyring`
directly, not the wasm, and the desktop roundtrip already passed).

## Verification
- Browser `register()` now returns the recovery mnemonic (no throw).
- Full register → login → onboarding flow reachable.
- web/mobile/extension tsc clean; biome clean; hermes verify green.
