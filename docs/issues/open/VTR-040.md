## What to build

Two hardening tasks:
- **Memory locking**: On desktop platforms, call `mlock()` on the heap pages holding the `Arc<DashMap<SecretHandle, ActiveSecret>>` to prevent swapping to disk.
- **Crash report sanitisation**: Configure Sentry (or alternative) to never capture local variables, minidumps, or request/response bodies. Add a `before_send` callback that scrubs any `uuid` from the event (unless it’s a safe breadcrumb). Ensure that `DecryptedSecret` never appears in the report.

## TDD Instructions

1. **Write a test** that forces the OS to swap (e.g., allocate large memory pressure), then verifies that the DashMap’s memory is not paged out (using platform API or `mincore` – if possible).
2. **Write a test** that triggers a crash (e.g., `panic!` in a controlled manner) and sends a report to a local Sentry mock; assert that the report contains no `DecryptedOverview` fields, no `Zeroizing` data, and no `password` strings.
3. **Write a test** that a crash report still contains the stack trace and breadcrumbs (e.g., “SyncStarted”, “KeyUpdateRequired”) but not the user’s email or item titles.
4. **Write a test** that ensures the Sentry SDK is initialised only after user consent (telemetry opt‑in).
5. **Write a test** that the `mlock` call is only executed on desktop (feature‑gated) and does not cause issues on platforms that don’t support it (e.g., WASM).

Implementation: use `libc::mlock` for Unix, `VirtualLock` for Windows. For Sentry, use the Rust `sentry` crate with `attach_minidumps = false`.

## Acceptance criteria

- [ ] Decrypted secrets never appear in crash reports (verified via audit).
- [ ] The DashMap memory is locked in RAM (desktop only).
- [ ] Crash reports contain only anonymous state information.
