## What to build

A k6 load test suite (`test/load/sync.js`) that:
- Simulates 50 concurrent users.
- Each user performs a mix of `GET /sync/pull`, `POST /sync/push-batch` (updates), and `GET /items/{uuid}`.
- Measures p95 latency, error rate, and SQLite busy timeouts.
- Assert that OCC conflicts are < 1% of total updates (acceptable) and no deadlocks.

## TDD Instructions

1. **Write a k6 script** that runs for 5 minutes with 50 VUs, each user randomly updating their own set of 10 items; assert that no request times out (> 5s) and p95 < 500ms.
2. **Write a scenario** where two users (Alice and Bob) concurrently edit the same item (simulated by using a shared UUID pool) – assert that only one succeeds per version and 412 responses are handled gracefully.
3. **Write a test** that measures WAL growth during the load test – must stay under 100MB (configured checkpointing).
4. **Write a test** that checks the server’s memory consumption – RSS < 200 MB for 50 users.
5. **Write a test** that gradually ramps up to 100 concurrent users – find the breaking point and document.

Implementation: k6 script uses custom `setup` to create test users and items. Server must be deployed on a reference machine (2 vCPU, 4 GB RAM).

## Acceptance criteria

- [ ] All SLOs (p95 < 500ms, error rate < 0.1%) are met for 50 users.
- [ ] SQLite busy timeouts are zero (or negligible).
- [ ] The test is integrated into nightly CI.
