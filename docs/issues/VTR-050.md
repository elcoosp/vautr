## What to build

Complete the offline‑first story:
- Client queues mutations (saves, deletes) when offline, storing them in a local `offline_queue` table.
- Each queue entry includes the `DomainModel` (or delete intent) and the `sync_epoch` at the time of the edit.
- On reconnection, the `PersistenceWorker` replays the queue in order.
- If a conflict (412) occurs during replay, the user is prompted (modal) to resolve, then the queue entry is either retried or discarded.

## TDD Instructions

1. **Write a test** that goes offline, creates 5 items, then comes online – assert all 5 are pushed via `push-batch` and the queue is emptied.
2. **Write a test** where two offline edits conflict with server changes (simulate by having another device update the same items offline). When the first client comes online, it shows a conflict modal for each conflicting item, and after user resolution, the queue entry is updated or removed.
3. **Write a test** that the queue respects the `sync_epoch`: if the epoch changes while offline (e.g., key rotation), the queued mutations are discarded and the user is asked to re‑authenticate.
4. **Write a test** that the queue persists across app restarts (table is saved) and replay resumes correctly.
5. **Write a test** that the queue order is preserved: if item A was created offline then item B was edited, replay must push A then B.

Implementation: add `offline_queue` table with fields: `id`, `command_type`, `payload_json`, `sync_epoch`, `created_at`. The `PersistenceWorker` checks online status via a network listener.

## Acceptance criteria

- [ ] Offline queue can hold up to 1000 entries without performance degradation.
- [ ] Replay is atomic per batch (if one fails, the rest are still attempted).
- [ ] The UI shows a sync progress indicator for replay.
