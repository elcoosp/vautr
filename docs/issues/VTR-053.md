## What to build

Audit log for compliance (GDPR, self‑hosters):
- Log events: `user_created`, `user_logged_in`, `user_logged_out`, `account_deleted`, `reclaim_initiated`, `reclaim_completed`.
- Each log entry includes: timestamp, user_id (hashed), event_type, IP address (optional, can be disabled).
- **No** item UUIDs, no email addresses (except hashed), no payload information.
- Logs are written to a separate SQLite table or a JSON file (configurable) and rotated daily.

## TDD Instructions

1. **Write a test** that performs a login, then checks the audit log table – asserts an entry with `event_type = 'user_logged_in'` and a hashed user_id (not the raw email).
2. **Write a test** that deletes an account and verifies a `account_deleted` entry is written **before** the user’s data is purged.
3. **Write a test** that the audit log does **not** contain any item UUIDs or encrypted payloads.
4. **Write a test** that the audit log rotation keeps only the last 90 days of logs (configurable).
5. **Write a test** that an administrator (with special role) can view the audit log via a restricted endpoint (authenticated, rate‑limited).

Implementation: middleware that logs events after they succeed. Use `tracing` to write to a dedicated file or SQLite table.

## Acceptance criteria

- [ ] No PII (email, IP optional) is stored in audit logs.
- [ ] Logs are tamper‑evident (digital signature optional for compliance).
- [ ] Self‑hosters can disable audit logging entirely.
