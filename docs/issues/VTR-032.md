## What to build

In `vautr-keyring`:
- `wrap_svk_with_mp(svk: &SymmetricVaultKey, mk: &MasterKey) -> WrappedSVK` (AEAD with KEK derived from MK).
- `wrap_svk_with_rk(svk: &SymmetricVaultKey, rk_bytes: &[u8; 32]) -> WrappedSVK`.
- `recover_via_rk(rk_mnemonic: &str) -> Result<SymmetricVaultKey, RecoveryError>` that decodes BIP‑39, derives KEK_RK, unwraps `WrappedSVK_RK`, then forces MP reset.
- After recovery, call `rotate_mp_and_rk(new_mp: Zeroizing<String>)` to generate new MP KEK, new RK (BIP‑39), re‑wrap SVK, and push to server.

## TDD Instructions

1. **Write a test** that creates a vault, exports the RK, then recovers using the RK (without MP) – must return the same SVK.
2. **Write a test** that after recovery, calling `rotate_mp_and_rk` generates a new RK (different mnemonic) and the old RK can no longer unlock.
3. **Write a test** that supplies an invalid BIP‑39 mnemonic (checksum error) – returns `RecoveryError::InvalidMnemonic`.
4. **Write a test** that recovers, then attempts to call `unlock_with_password` with the old MP – must fail (the server’s OPAQUE record was rotated).
5. **Write a test** that the emergency kit PDF is generated locally (no network) and contains the 24 words but no QR code.

Implementation: use `bip39::Mnemonic`, `hkdf`, and AEAD from VTR-012. The server must store two wrapped SVK blobs: one for MP, one for RK.

## Acceptance criteria

- [ ] The RK is never stored on the server (only the wrapped SVK under RK KEK).
- [ ] Recovery does **not** require an internet connection (only to fetch the wrapped blob).
- [ ] The PDF generation uses a local HTML template and a PDF renderer (e.g., `printpdf`).
