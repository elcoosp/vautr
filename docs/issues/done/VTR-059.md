## What to build

Server endpoints and client UI for:
- `POST /auth/logout` – invalidates current session token.
- `GET /auth/sessions` – returns list of active sessions (device name, last active IP, created time) – but careful with PII; only show device name (user‑provided) and last activity date.
- `DELETE /auth/sessions/{session_id}` – revokes a specific session.
- `DELETE /auth/sessions` – revokes all other sessions (keep current).
- On revoke, the server adds the token to a blacklist (Redis or database) for the duration of its natural expiry.

## TDD Instructions

1. **Write a test** that logs in from two devices (simulated by different tokens), then revokes all other sessions from one device – asserts the other device’s token is invalidated (returns 401).
2. **Write a test** that logs out from a device; the token becomes invalid immediately.
3. **Write a test** that the session list shows only the device name (which the user can set during login) and the last activity time (not IP).
4. **Write a test** that a revoked session cannot be used even if it is still within its expiry window.
5. **Write a test** that the blacklist survives server restart (using Redis persistence or a database table).

Implementation: store session tokens in a `sessions` table with `user_id`, `token_hash`, `device_name`, `created_at`, `last_used_at`. On revoke, delete the row or mark as revoked.

## Acceptance criteria

- [ ] User can see and revoke active sessions from the security settings.
- [ ] Revoking a session does not affect other sessions.
- [ ] The session list does not leak PII (IP addresses, exact timestamps optional).
