## What to build

Client‑side telemetry module (optional, user‑controlled) that:
- Maintains an in‑memory aggregator of metrics: counters, histograms, min/max.
- Every 24 hours, sends a single heartbeat to a telemetry endpoint containing:
  - Installation UUID (random, non‑PII).
  - Aggregated metrics (e.g., `sync_duration_ms` histogram buckets, `crypto_ops` counters).
  - App version, OS version.
- Does **not** send any UUIDs, item titles, or timestamps of individual events.

## TDD Instructions

1. **Write a test** that simulates 10 sync operations with varying durations, then triggers the 24‑hour flush – asserts the outgoing JSON contains aggregated histograms (p50, p95, p99) but no raw values.
2. **Write a test** that disables telemetry (user opt‑out) – asserts no network request is made.
3. **Write a test** that crashes the app before the 24‑hour flush; the aggregator is reset on next start (no partial data is kept).
4. **Write a test** that ensures the installation UUID is persisted across restarts (in local storage) but is never sent alongside any user identifier.
5. **Write a test** that the telemetry endpoint returns 200 and the client marks the batch as sent; on network failure, it retries on next heartbeat.

Implementation: use `dashmap` for concurrent counters, `serde` for JSON, and a `tokio::time::interval` task. The heartbeat URL is configurable.

## Acceptance criteria

- [x] No PII (email, UUIDs of items, URLs, titles) ever appears in telemetry. (`HeartbeatReport` carries only `InstallationUuid` + os/app version + integer-only `AggregatedMetrics`; controller tests `tdd4` assert no `user_id`/`email`/`username` in the payload. `Histogram` keeps a bounded reservoir for percentiles but never serializes it.)
- [x] The heartbeat is sent at most once per 24 hours per installation. (`DailyAggregator` rolls a window exactly every `WINDOW_24H`; `TelemetryController::tick`/`start` send one report per rolled window; sub-24h ticks are no-ops.)
- [x] Telemetry is off by default (requires user consent on first launch). (`ConsentGate` defaults to `Denied`; every `record_*` method is a no-op until `grant_consent()`, and `tick` is a no-op without consent or a sender — `tdd2` proves no network request when disabled.)

## Notes

- `vautr-telemetry` already had the aggregator/consent/report/monitoring primitives. This pass added the missing client half: `Histogram` percentiles (p50/p95/p99 via bounded reservoir), `sender` module (`HeartbeatSender` trait + `RecordingSender`/`FailingSender` test doubles + `HttpHeartbeatSender` behind `http` feature), and `controller` (`TelemetryController` tying aggregator + consent + sender into the 24h loop with retry-on-failure and an injectable sender for tests; `start` background loop behind `tokio` feature).
- All 5 TDD scenarios are covered by passing tests (`tdd1`–`tdd5` in `controller.rs`), plus percentile/histogram tests in `aggregate.rs`. `cargo test -p vautr-telemetry --features tokio,http` → 32 passed.
- Embedding apps (web/extension/mobile) persist `InstallationUuid` and wire a `HttpHeartbeatSender` + call `record_*` from the sync/crypto paths; that client integration is a follow-up (out of scope here, which is the server/crate library).
