## What was built

Closed the extension's key-rotation gap (the only cleanly-buildable slice of the
former "extension sharing/rotation/quarantine" parity item — see CLIENT_PARITY.md
gaps #3–#5). Sharing and quarantine reaper remain backend/client-crypto-gated
and are intentionally left for dedicated VTRs, not stubbed.

### Client crypto (VautrWebClient)
- `packages/vautr-client-sdk/src/realClient.ts`: added `rotateKey(password)` and
  `getKeyGen()`. `rotateKey` re-reads the persisted `kdfSalt`, re-derives the KEK
  from the master password, re-wraps the in-memory `svk` via the wasm
  `AsyncCryptoAdapter.wrapSvk`, then `POST /account/rotate-key` with
  `{ new_min_enc_key_gen: min_enc_key_gen + 1, new_svk_ciphertext_blob }`. On
  success it advances `localKeyGen` and persists it. Mirrors the desktop
  orchestrator's `rotate_key`; the server-backed client does it explicitly because
  it does not retain the master password in memory (the user re-enters it).
- No new crypto primitive required — `deriveMasterKey` / `deriveKek` / `wrapSvk`
  were already on `AsyncCryptoAdapter` (used by `register`).

### Extension UI
- `apps/extension/src/popup/components/MfaTab.tsx`: added a "Vault key rotation"
  card (security surface) showing the current generation and a master-password
  confirm field + "Rotate vault key" button calling `client.rotateKey`.
- `apps/extension/src/popup/App.tsx`: passes `client` into `<MfaTab>`.
