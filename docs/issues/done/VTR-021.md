## What to build

A `KeyRotation` component in `vautr-keyring` with method `rotate_svk(new_svk: SymmetricVaultKey)` that:
- Calls `POST /account/rotate-key` to increment server `min_enc_key_gen`.
- Queries local DB for items where `enc_key_gen < new_gen`, processes in batches of 100.
- For each batch: decrypt with old SVK, re‑encrypt with new SVK, update local `enc_key_gen`, push batch via `POST /sync/push-batch`.
- After crash, resumes from the next batch (items still at old `enc_key_gen`).

## TDD Instructions

1. **Write a test** that creates 250 items (enc_key_gen=1), initiates rotation to gen=2, and asserts all batches are sent and DB updated.
2. **Write a crash simulation test** that kills the rotation after the first batch, re‑initialises the client, and asserts rotation resumes from batch 2 (items 101‑200).
3. **Write a test** where server returns 422 `key_generation_too_old` on a batch – asserts rotation stops and error is reported.
4. **Write a test** using `wiremock` that simulates network failure on batch 2; after retry, the same batch is pushed again (idempotent).
5. **Write a concurrency test** that tries to rotate while a normal `save_item` is in flight – must not corrupt state.

Implementation: store rotation progress in `sync_meta` (no extra table). Use `tokio::spawn` for background worker.

## Acceptance criteria

- [ ] Rotation is resumable after any crash.
- [ ] No items are re‑encrypted twice (idempotent).
- [ ] The `enc_key_gen` column acts as the cursor.
