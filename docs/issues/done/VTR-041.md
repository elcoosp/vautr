## What to build

Extend sharing to groups (1:N):
- Create group: generate a random 32‑byte `GroupSIK`, store locally.
- Add member: fetch member’s public key, wrap `GroupSIK` using KEM (same as VTR-026), store wrapped blob on server.
- Revoke member: generate new `GroupSIK`, re‑encrypt all shared items with new SIK, re‑wrap for remaining members, delete revoked member’s wrapped keys.
- Server endpoints: `POST /groups`, `POST /groups/{id}/members`, `DELETE /groups/{id}/members/{user_id}`.

## TDD Instructions

1. **Write a test** that creates a group with 3 members, shares an item, then each member unwraps the Group SIK and decrypts the item – all succeed.
2. **Write a test** that revokes a member, then attempts to unwrap the new Group SIK (the revoked member’s wrapped key is gone) – fails, and the item is re‑encrypted with the new SIK for remaining members.
3. **Write a test** that adds a new member to an existing group; the new member can decrypt all past shared items (Group SIK is static until revocation).
4. **Write a test** that a revoked member’s offline client still has the old SIK but cannot sync new updates (server rejects with 403 on pull).
5. **Write a performance test** that revokes a member from a group with 100 shared items – the re‑encryption and re‑wrapping completes within 2 seconds.

Implementation: add `groups` and `group_members` tables on server. Group SIK is stored encrypted under each member’s public key (no server‑side plaintext).

## Acceptance criteria

- [ ] Revocation is cryptographic – no backdoor.
- [ ] Adding a new member does not require re‑encrypting existing items.
- [ ] All group metadata (member list) is encrypted on server (only wrapped keys visible).
