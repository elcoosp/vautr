# VTR-070 — Mobile sharing + client parity (uniffi FFI, native bridges, group UI, export)

## Context (why)
Web/extension (VTR-066/067) and desktop share items via the `vautr-sharing` PKI, but
the **mobile** client (`apps/mobile`, React Native + Expo) had no sharing surface, and
the **desktop** client lacked the group-sharing flow that web/ext/mobile gained. The
zero-knowledge invariant must hold on every client: plaintext secret bytes must be
produced inside Rust and never sit in the JS heap (web/ext use WASM; mobile/desktop
use the uniffi `MobileClient` / `VautrClient` directly).

This issue expanded well beyond its original 1:1 mobile-sharing scope (the stale
`closed/VTR-070.md` described only the FFI surface). The full delivered scope:

## What shipped

### 1. Rust FFI sharing surface (`core/vautr-ffi`)
- `src/sharing.rs` (new): uniffi exports for the ZK sharing primitives —
  `ffi_share_item`, `ffi_accept_share`, `ffi_create_group`, `ffi_add_group_member`,
  `ffi_unwrap_group_key`, `ffi_encrypt_group_item`, `ffi_decrypt_group_item` — plus
  `FfiShareBundle` / `FfiWrappedGroupKey` / `FfiGroupKey` / `FfiSharingKeyPair` records.
- `src/client.rs`: `MobileClient` gains sharing methods (share/accept/group) delegating
  to `crate::sharing::*`; plaintext returned only to native callers.
- `src/lib.rs`: two sharing roundtrip tests (1:1 + group). **5 vautr-ffi lib tests green.**

### 2. Native bridges (iOS + Android) — BUILT GREEN THIS SESSION
- **iOS** (`packages/native`): uniffi Swift bindings + `VautrNativeModule` (Expo
  TurboModule) wired; `xcodebuild` → **BUILD SUCCEEDED** (commit cf4b852).
- **Android** (`packages/nautr/native` → `expo.modules.vautr.bridge`): Gradle module +
  `libvautr_ffi.so` (arm64-v8a) built via `cargo ndk`; `gradlew :app:assembleDebug`
  → **BUILD SUCCESSFUL** (commit 5b4c56f). Required fixes: expo-module-gradle-plugin,
  JNA dep, Kotlin `runBlocking` wrappers for all uniffi `suspend` calls, package rename
  off the Java keyword `native`.
- The stale claim "Not verifiable in this sandbox" is **FALSE** — both native builds
  were executed and verified in this environment.

### 3. sea_orm 2.0.2 migration (`core/vautr-db`)
- Entities migrated to the `#[sea_orm::model]` attribute-macro form (relations on the
  `Model` struct), NOT derive/`DeriveEntityModel`, targeting sea_orm 2.0.2
  (commit 4ab0e69). `cargo test -p vautr-db` → 7 passed.

### 4. Group-sharing UI parity (web / extension / mobile)
- **Web** (`apps/web`): `GroupsView`, `ItemDetail` group section — group create,
  add-member, share-to-group, group inbox + accept-invite.
- **Extension** (`apps/extension`): same group flows via the WASM sharing primitives.
- **Mobile** (`apps/mobile/src/routes/_app.shares.tsx`): rewritten to full parity —
  create group, add member, share item to group, group inbox + accept-invite, list
  group items. `MobileSharingClient` caches the Group SIK and exposes
  `getGroupInbox`/`getGroupKey` (commit 8b76e41). **SDK 10/10, mobile 6 passed.**

### 5. Desktop local vault JSON export (ZK-preserving)
- `vautr_app_state::VautrClient::export_to_json` exposed via desktop UI
  (`apps/desktop/src/desktop_view.rs`): an "Export vault (JSON)" card writes the
  plaintext vault JSON to a local file (default `~/vautr-vault-export-<ts>.json`).
  Desktop-only — web/ext deliberately do NOT get plaintext-in-JS export (ZK invariant);
  they use the encrypted server `/backup/export` instead.
- FFI `export_vault()` added to the `desktop-api`-gated impl block (compiled out of
  mobile/web/ext) (commit 928cdec).

### 6. Desktop group-sharing UI (this session)
- Extended the existing share modal (`render_share_modal`) with a group section:
  create group, add member to active group, share pending item to active group. Uses
  `VautrClient::create_group` / `add_group_member` / `share_to_group` directly
  (desktop drives `vautr_app_state` natively). Plaintext revealed locally
  (`reveal_secret` → `read_secret`) then encrypted under the Group SIK — no JS heap
  exposure. (`do_add_group_member` renamed to avoid a clash with the pre-existing
  project-member `do_add_member`.)

## Zero-knowledge invariant
Plaintext secret bytes are produced only inside Rust (uniffi `MobileClient` /
`VautrClient`) and handed back to the native caller; the JS layer holds only opaque
base64 / handles. Web/extension use WASM and never reconstruct plaintext in JS for
export. Matches the desktop secure-overlay pattern (VTR-048) and the web/ext WASM
pattern (VTR-061).
