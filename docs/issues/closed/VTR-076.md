# VTR-076 — Dedicated Emergency Kit surface

**Problem.** The first-run onboarding "Save your Emergency Kit" step (step 3 on
all four clients) currently deep-links to *MFA & security*, where only TOTP
recovery codes are shown. There is **no dedicated Emergency Kit surface** on any
client — yet the server already implements the full kit:

- `core/vautr-server/src/handlers/recovery.rs` — kit issue/export endpoints.
- `core/vautr-files/src/pdf.rs` — renders the kit as a downloadable PDF.
- `core/vautr-app-state/src/recovery.rs` + `vautr-keyring` — BIP-39 24-word
  mnemonic ("Emergency Kit") generation + recovery codes.
- `apps/desktop/src/auth_client.rs:57` confirms the 24-word BIP-39 mnemonic is
  the kit payload.

So the onboarding copy ("save your Emergency Kit") points at a page that does
not exist. This is the cross-platform gap flagged at the end of VTR-073/074/075.

**Goal.** Build a dedicated Emergency Kit screen/route on each client that:
1. Generates (or fetches) the kit: BIP-39 24-word mnemonic + recovery codes.
2. Offers copy + PDF download (the server can render the PDF; clients can also
   render locally, but server PDF is the canonical artifact).
3. Shows the "store somewhere safe" warning (matches onboarding copy).
4. Is the deep-link target of the onboarding emergency-kit step (replace the
   MFA & security link).

**Resolved design (deviation from original scope — ZK-correct).** The original
issue assumed a *server-generated* kit/PDF per client. The implemented design is
**client-local and zero-knowledge**: the BIP-39 Recovery Key mnemonic is
generated at `register()` (already happens inside the SDK's `register()`), then
KEK-sealed and persisted at rest (never plaintext; server only ever stores the
wrapped SVK-RK blob, never the mnemonic). The kit is therefore rendered entirely
on-device — no new server endpoint was needed. This matches the zero-knowledge
invariant strictly better than shipping the mnemonic to the server for PDF
rendering.

**What shipped (VTR-076).**
- SDK (`packages/vautr-client-sdk`): `register()` now returns
  `{ recoveryMnemonic }`; seals it under the KEK via `wrap_svk` AEAD and persists
  `recoveryMnemonicEnc` (base64) in `StoredState`. `getEmergencyKit()` decrypts it
  locally (unsealed into an in-memory cache at login; cleared on lock).
- Web/Extension: onboarding Emergency Kit step shows the mnemonic once
  (reveal/copy/download HTML). Settings (web) / MFA tab (ext) add an "Emergency
  Kit" card with reveal/copy/download. `lib/kit.ts` `renderKitHtml` produces a
  printable kit document.
- Mobile (`apps/mobile`): `VautrAuth.register` KEK-seals the mnemonic into the
  keychain; `getEmergencyKit()` returns it. Onboarding + Settings card with
  reveal/copy/share. `lib/kit.ts` `renderKitHtml` + RN `Share`.
- Desktop (Rust/GPUI): `VaultConfig.recovery_mnemonic_enc` (KEK-sealed, TOML).
  `do_register` seals + persists + caches; `do_login` unseals. Settings renders
  an Emergency Kit card (reveal/copy) and "Download" writes
  `~/Downloads/vautr-emergency-kit.html` via `render_kit_html`.

**Zero-knowledge note.** The mnemonic is generated client-side and stored only
KEK-encrypted at rest; the server never receives it. At-rest blob is opened
locally from the keychain/config.
