## What to build

Rate limiting middleware (using Redis) on critical endpoints:
- `/auth/login/start` and `/auth/register/start`: 5 per minute per IP/email.
- `/sync/pull`: 30 per minute per user.
- `/sync/push-batch`: 10 per minute per user.
- Response headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, and `Retry-After` on 429.

## TDD Instructions

1. **Write a test** that sends 6 `/auth/login/start` requests in 10 seconds – the 6th must return 429 with `Retry-After` header.
2. **Write a test** that waits the exact `Retry-After` seconds (using mocked time) and then a request succeeds.
3. **Write a test** that the rate limit is per‑user (different users have independent limits) – not sharing a global bucket.
4. **Write a test** that the `X-RateLimit-Reset` header contains a Unix timestamp matching the next window.
5. **Write a test** that after the limit is reached, the client sees the headers and can implement exponential backoff.

Implementation: use `redis` crate and a sliding window counter (or token bucket). Store in Redis with expiry. The middleware extracts user ID from auth token (or IP for unauthenticated endpoints).

## Acceptance criteria

- [ ] Rate limits are configurable via environment variables.
- [ ] A 429 response includes a human‑readable `Retry-After` (seconds or HTTP date).
- [ ] Rate limits survive server restart (persisted in Redis).
