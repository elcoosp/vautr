## What to build

A function `resolve_conflict(uuid: Uuid, local_version: u64, server_metadata: ItemMetadata, is_toxic: bool)` in `vautr-sync` that:
- Updates the DashMap with `ignored_version = server_version` and `state = ToxicIgnored` or `ValidIgnored`.
- Emits a `ConflictEvent` to the UI event bus.
- After user choice (overwrite/keep), either removes the item from DashMap or leaves it.

## TDD Instructions

1. **Write a test** that simulates a 412 response with `is_toxic=true`. Call `resolve_conflict`; assert DashMap now contains the uuid with `state=ToxicIgnored` and `ignored_version=server_version`.
2. **Write a test** that simulates user choosing “Overwrite Server”; assert the DashMap entry is removed.
3. **Write a test** that simulates user choosing “Keep Local” (discard); assert the DashMap entry remains (preserving ignore intent).
4. **Write a test** for valid conflict (`is_toxic=false`) – same checks, but state is `ValidIgnored`.
5. **Write a test** that checks the UI event `VaultStateUpdate::ConflictDetected` is broadcast with the correct `ConflictEvent` data.

Implementation: use `Arc<DashMap>` and an event bus channel. The “user choice” is simulated by calling a second method `resolve_with_choice(uuid, choice)`.

## Acceptance criteria

- [ ] DashMap updates are atomic (no race between read and write).
- [ ] The conflict event includes `is_toxic` flag so UI can show different modals.
- [ ] After resolving by overwrite, the next sync pull will download the new payload.
