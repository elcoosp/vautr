# Vautr Emergency Recovery & Account Lifecycle Architecture

This document defines the exact cryptographic mechanisms, user flows, and lifecycle boundaries for recovering a Vautr vault in the event of a lost Master Password, and the secure protocols for account deletion and device rotation. 

In a true Zero-Knowledge system, there are no backdoors. If a user loses their Master Password (MP) and has no recovery mechanism, their data is cryptographically irrecoverable. This specification defines the emergency escape hatch—a cryptographically equivalent Recovery Key—while preserving the Zero-Knowledge guarantee, maintaining rigorous physical security boundaries, and solving the network authentication paradox inherent in credential rotation.

Deviations from this specification will result in either catastrophic data loss for users or the introduction of physical/network exfiltration vectors that void the Zero-Knowledge guarantee.

---

## 1. The Recovery Philosophy (The Human Boundary)

1.  **The Binary State:** A vault is either 100% recoverable or 0% recoverable. There is no partial recovery, no "password hints," and no server-side key escrow.
2.  **The Master Key Equivalence:** The Recovery Key (RK) is mathematically equivalent to the Master Password for the sole purpose of unwrapping the Symmetric Vault Key (SVK).
3.  **The "Paper Key" Paradigm:** The RK is a high-entropy secret that must exist outside the user's digital footprint. It is framed in the UI as an "Emergency Kit"—something to be printed, written down, and stored in a physical safe.
4.  **Forced Rotation:** Using the RK to recover a vault is a high-friction, emergency-only operation. Upon successful recovery, the user is forced to set a new Master Password and rotate the Recovery Key.

## 2. Cryptographic Recovery Mechanism (Dual-Wrapping & Auth)

To allow recovery without a server-side backdoor, the SVK is encrypted twice. Furthermore, because the user cannot authenticate via OPAQUE without the forgotten MP, the RK must also provide a cryptographic path to authenticate the recovery request to the server.

### 2.1 The Recovery Key Generation
*   **Source:** 32 bytes (256 bits) generated by the OS CSPRNG (`OsRng`).
*   **Format:** The 32 bytes are encoded into a 24-word BIP-39 mnemonic for human readability and offline transcription.
*   **Mapping:** To use the RK, the BIP-39 mnemonic is decoded back into the exact 32 bytes.

### 2.2 The Dual-Wrapping & Auth Key Tree
When a vault is created or the MP is changed, the Core performs dual-wrapping and registers an authentication credential:

1.  **MP Path (Standard):** `MP -> Argon2id -> MK -> HKDF(MK, "vautr-kek") -> KEK_MP`. The SVK is encrypted: `WrappedSVK_MP = AEAD_Encrypt(KEK_MP, AD="vautr-mp-wrap", SVK)`.
2.  **RK Path (Recovery):** `RK_Bytes -> HKDF(RK_Bytes, "vautr-rkek") -> KEK_RK`. The SVK is encrypted: `WrappedSVK_RK = AEAD_Encrypt(KEK_RK, AD="vautr-rk-wrap", SVK)`.
3.  **RK Authentication Path:** `RK_Bytes -> HKDF(RK_Bytes, "vautr-rk-auth") -> Ed25519_PrivateKey`. The corresponding `RK_PubKey` is generated.

Both `WrappedSVK_MP`, `WrappedSVK_RK`, and the `RK_PubKey` are sent to the server and stored in the `sync_meta` table.

### 2.3 The Recovery Flow (Unlock, Auth, & Mandatory Rotation)
When the user forgets their MP but possesses the RK:

1.  **Input & Derive:** User enters the 24-word BIP-39 mnemonic. Client decodes to `RK_Bytes`, derives `KEK_RK`, and derives the `Ed25519_PrivateKey`.
2.  **Server Authentication (The Recovery Gate):**
    *   **Challenge:** Client requests a recovery challenge: `GET /account/recover/challenge`. The server returns a cryptographic nonce.
    *   **Prove Possession:** Client signs the nonce with the `Ed25519_PrivateKey`.
    *   **Verify:** Client sends the signed nonce to `POST /account/recover/verify`. The server verifies the signature against the stored `RK_PubKey`. If valid, the server issues a short-lived, one-time-use `RecoverySessionToken`.
3.  **Unwrap & Unlock:** Client downloads `WrappedSVK_RK`, decrypts it with `KEK_RK` to obtain the `SVK`, and unlocks the vault locally.
4.  **Forced MP Reset:** The UI forces the user to create a new Master Password.
5.  **Mandatory RK Rotation:** The Core generates a new 32-byte RK, derives a new `KEK_RK` and a new `Ed25519` keypair.
6.  **Re-wrap & Complete:** The Core derives a new `KEK_MP`. It re-wraps the SVK into new `WrappedSVK_MP` and `WrappedSVK_RK` blobs. It generates a new OPAQUE registration payload.
7.  **Push:** Client pushes the new OPAQUE registration, wrapped keys, and new `RK_PubKey` to `POST /account/recover/complete`, authenticating with the `RecoverySessionToken`. The server atomically replaces the old credentials. The user must save a new Emergency Kit.

## 3. The Emergency Kit (UX & Physical Security)

The Emergency Kit is the physical manifestation of the RK access path. It must be generated, validated, and handled securely, prioritizing resistance to rapid, automated physical exfiltration.

### 3.1 The PDF Generation
*   **Local Only:** The PDF is generated entirely on the client device. The RK is *never* transmitted to a server.
*   **Contents:** The PDF contains the Vautr logo, clear physical storage instructions, the user's email address, and the 24-word BIP-39 mnemonic in a readable format.
*   **The No-QR-Code Rule:** The PDF **MUST NOT** contain a QR code or any machine-scannable representation of the RK. BIP-39 words exist specifically to resist rapid, automated exfiltration. A QR code allows an attacker to photograph and steal the key from a distance in seconds. Human transcription is a deliberate security feature, not a bug.

### 3.2 Onboarding Validation (Proof of Possession Gate)
To ensure the user actually saved the Emergency Kit, the onboarding flow enforces a validation step immediately after generation.
1.  **Challenge:** The UI hides the mnemonic and prompts: "To confirm you saved your Emergency Kit, please enter word 4, word 12, and word 20."
2.  **Verification:** The client checks the entered words against the generated `RK_Bytes` (utilizing the built-in BIP-39 checksum to reject typos immediately).
3.  **Enforcement:** The user cannot finish onboarding or use the vault until this validation passes.

## 4. Account Reset & Deletion Lifecycle

Define what happens when a user cannot recover and must start over, or chooses to delete their account.

### 4.1 Authenticated Deletion (Standard)
If the user is logged in and requests account deletion:
1.  **Core Action:** The Core deletes the local SQLite DB securely (overwriting file contents before deletion).
2.  **Server Action:** The authenticated client calls `DELETE /account`. The server permanently deletes all user metadata, `WrappedSVK` blobs, and encrypted item payloads from Postgres.
3.  **OPAQUE Retirement:** The server retires the OPAQUE registration record.

### 4.2 Unauthenticated Reclaim (The "I lost everything" Flow)
If the user forgets both the MP and the RK, their data is irrecoverable. However, they may want to reclaim their email address for a fresh start. **Security takes precedence over immediate data destruction to prevent Denial of Service (DoS) via email compromise.**
1.  **Email Verification:** The client initiates an "Account Reclaim" flow. The server sends a verification link to the registered email address.
2.  **Reclaim over Deletion:** Clicking the link authenticates the user to the server. The server immediately releases the email address, allowing the user to register a brand new, empty vault with that email.
3.  **30-Day Suspension:** The *old* vault data (encrypted blobs, OPAQUE record) is **not** immediately deleted. It is suspended and hidden. It is permanently purged from Postgres after a 30-day grace period.
4.  **Security Rationale:** If an attacker compromises a user's email, they could trigger an immediate deletion of the vault backups, causing irrecoverable data loss (DoS). The 30-day suspension gives the legitimate user a window to recover their email, log into the suspended Vautr account using their MP/RK, and reclaim their data before it is permanently purged.

## 5. Device Provisioning

When a user adds a new device, they must unlock the vault on that device. Vautr relies strictly on the cryptographically sound Server Sync Flow.

**The Standard Sync Flow (The Sole Provisioning Mechanism)**
Local device-to-device QR provisioning is explicitly excluded from the Vautr architecture. Transferring wrapped keys via QR is redundant (they can be downloaded from the server), and transferring unwrapped keys (the SVK) via a visual medium is a catastrophic security violation.

1.  **Download:** New device downloads the Vautr app.
2.  **Login:** User enters email and Master Password (or initiates the RK Recovery Flow using their physical Emergency Kit).
3.  **Derive & Sync:** The new device derives the MK, unwraps the SVK, and performs a full `GET /sync/pull` to populate its local SQLite DB.

---

## 6. Security Considerations & Trade-offs

*   **RK Compromise:** If an attacker obtains the Emergency Kit (RK) *and* the user's email/server credentials, they can fully decrypt the vault and authenticate a recovery. The physical security of the Emergency Kit is the single point of failure.
*   **BIP-39 Typo Resistance:** Standard BIP-39 includes a checksum. If a user miswrites one word, the decoding will fail with a checksum error, preventing them from deriving the wrong key.
*   **RK Rotation Performance:** Unlike a full SVK rotation (O(N) operation), rotating the RK or MP only requires re-wrapping the single SVK blob and generating a new OPAQUE record (O(1)). This makes post-recovery rotation fast and safe.
*   **Recovery Token Security:** The `RecoverySessionToken` is strictly short-lived and single-use. If the client fails to complete the recovery flow, the token expires, preventing replay attacks.
